1.4 DVC (data version control)

Toy part (folder dvc_toy, Figures 1.4a–h). These are the steps, in order: 1. git init and dvc init. 2. Create a 3-row data.csv, then dvc add data.csv. This creates the pointer data.csv.dvc and adds data.csv to .gitignore. Then commit (v1). 3. Append a row, run dvc add again and commit (v2). 4. git checkout HEAD~1 -- data.csv.dvc followed by dvc checkout brought back the 3-row version. git checkout HEAD -- data.csv.dvc and dvc checkout returned the 4-row version. 5. Add a local folder remote (dvc remote add -d localremote …) and dvc push. 6. Delete data.csv and .dvc/cache, then dvc pull. The pull printed "1 file fetched and 1 file added", so the file was restored from the remote. 7. Push the Git history to DagsHub (Rebelhere/L230518_A2_Ops_toy). DagsHub shows data.csv as a DVC-tracked file next to its pointer.

Apply. - I tracked the whole data/ folder with dvc add data, using DagsHub storage as the origin remote. - data.dvc (Figure 1.4i) holds the directory hash b2cec678…​.dir, the size (503,783,378 bytes) and the file count (975). - dvc status -c reports "Cache and remote 'origin' are in sync" (Figure 1.4j). - DagsHub and GitHub both show data as DVC-managed. Only the pointer is in Git (Figures 1.4k–l).

What the pointer file holds and why large data stays out of Git. - The .dvc file is a few lines of YAML: a content hash (md5), a size, a file count and a path. The hash is the address of the real content in the DVC cache and remote, so the Git commit pins exactly which data version the code used. - Git stores every version of every file forever and diffs them as text. A 500 MB image folder would bloat every clone, slow every operation, and exceed GitHub's size limits. - DVC stores the data once per content hash in cheap object storage and keeps Git small. - Every MLflow run is tagged with this hash (dvc_data_md5; see Chapter 3).

Chapter 2: Model development with TensorFlow/Keras

2.1 Input pipeline

src/data.py::make_ds builds a tf.data pipeline. The stages, in order: 1. Read split list. from_tensor_slices((paths, labels)) reads the paths and labels from splits/<split>.csv. Only these three lists are used, so no image can leak between splits. 2. Decode and resize. map(_load, AUTOTUNE) calls src/preprocess.py::decode_resize: - tf.io.decode_image(channels=3, expand_animations=False) handles both JPEG and PNG, forces 3 channels (drops alpha, expands greyscale and palette), and takes the first frame of a GIF-like file. - tf.image.resize makes the image 224×224 with bilinear interpolation, as float32 values in [0, 255]. 3. Cache. cache() keeps the decoded images in memory after the first epoch. Decoding 5–10 MB JPEGs is the most expensive step. 4. Shuffle. shuffle(len, seed=42, reshuffle_each_iteration=True) runs on training data only. 5. Augment (training data only): RandomFlip("horizontal"), RandomRotation(0.08), RandomZoom(0.15) and RandomContrast(0.15). These perturbations are mild, so they don't destroy the high-frequency artefacts that separate AI images from real ones. 6. Batch and prefetch. batch(32) then prefetch(AUTOTUNE) lets the CPU prepare the next batch while the model trains on the current one.

Image size. - 224×224 is the native ImageNet input of MobileNetV2, so the pretrained filters see objects at the scale they were trained on. - It is also small enough for CPU training.

Aspect ratio. - tf.image.resize stretches the image; it does not keep the aspect ratio. A 1024×576 image is squeezed horizontally. - I chose stretching over crop or pad because cropping can cut off the part of the image that shows the artefact, and padding adds black borders the model could learn to use. - The same stretch is applied in serving (Chapter 4), so training and serving still agree.

Loss. Binary cross-entropy is the correct likelihood for a single sigmoid output with 0/1 labels.

Optimizer. Adam at lr = 1e-3 gives robust default step sizes, so it needs no hand-tuned schedule (ReduceLROnPlateau handles the rest).

Metrics. Accuracy, precision, recall and AUC. Because the classes are imbalanced and the two errors cost differently (see 2.5), accuracy alone isn't enough. AUC measures ranking quality independently of the threshold.

2.3 Transfer learning (MobileNetV2)

src/models.py::build_mobilenet loads keras.applications.MobileNetV2(include_top=False, weights="imagenet"), which leaves out the 1000-class classifier.

Head. GAP, then Dropout(0.3), then Dense(1, sigmoid).

Preprocessing. - mobilenet_v2.preprocess_input maps [0, 255] to [-1, 1], which is the scaling MobileNetV2 was pretrained with. Feeding [0, 1] or [0, 255] would shift every activation, and the pretrained filters would then see "wrong" inputs. - I put this step inside the model graph. The saved .keras file therefore contains it, and the serving code cannot forget it.

Stage 1 (frozen base). - base.trainable = False, and the base is called with training=False so BatchNorm stays in inference mode. - The only trainable weights are dense_1/kernel and dense_1/bias: 1,281 parameters. - Adam lr = 1e-3, up to 15 epochs.

Stage 2 (fine-tune the last block). unfreeze_last_block sets trainable=True only for the block_16_* layers and Conv_1: - block_16_expand, block_16_expand_relu, block_16_depthwise, block_16_depthwise_relu, block_16_project and Conv_1; - 880,321 trainable parameters; - BatchNorm layers stay frozen, so the small batches don't corrupt their running statistics; - recompiled with a much smaller learning rate (1e-5 for the first runs, 1e-4 for the best one) for up to 10 epochs.

The small learning rate lets the pretrained features shift slightly toward "AI vs real" cues without erasing what they learned from ImageNet.

2.4 Training discipline

Seeds. keras.utils.set_random_seed(42) seeds Python, NumPy and TF, and the split and the shuffle also use seed 42.

Callbacks (src/train.py::fit_stage), on every stage: - EarlyStopping(val_loss, patience=5, restore_best_weights=True); - ModelCheckpoint(models/<run>_<stage>.keras, monitor=val_loss, save_best_only=True); - ReduceLROnPlateau(val_loss, factor=0.3, patience=2, min_lr=1e-7).

Best epoch. The best epoch (lowest val_loss) of each stage is logged as best_epoch_stage1/2 and marked with a red dashed line in the curves.

Transfer learning wins on every metric. The CNN's AUC of 0.67 shows that 681 images aren't enough to learn good features from scratch.

Which error is worse. - For VisionGuard, calling a real photo fake (a false positive) is worse. It can wrongly accuse a photographer or journalist of fabrication, damage their reputation, and get real evidence dismissed. - Missing an AI image leaves the user where they were without the tool.

Threshold choice. - The F1-optimal threshold (0.366) flags 30 of 66 real test photos as AI (FPR 45%), which is unacceptable for this product. - scripts/threshold_table.py and scripts/pick_threshold.py scan the validation ROC curve (Figure 2.5d). They pick the threshold with the highest AI recall subject to FPR ≤ 20%, which gives t = 0.771. - Youden's J would pick 0.836, which is even stricter.

The test false-alarm rate (18%) matches the validation target (20%), so the threshold generalised. The deployed app uses t = 0.771, read from the THRESHOLD environment variable.

Which setting mattered most. - The number of unfrozen layers, together with the learning rate. With 0 unfrozen layers, the results range from 0.58 to 0.75 depending only on lr. The worst trial (lr 1.1e-4, frozen) simply had not converged in 6 epochs. - Unfreezing 60 layers gave the two best AUCs (0.773 and 0.748). - Dropout between 0.2 and 0.4 had no consistent effect.

This agrees with my manual runs (3.5): fine-tuning more of the network with a moderate learning rate helped most.

Why choosing the best validation score can overfit the validation set. - The validation set has only 146 images, and one image is worth about 0.7 percentage points of accuracy. - Over many trials, some configurations win partly by luck on those particular images. Taking the maximum selects that luck, which is a winner's curse: the best trial's validation score is optimistically biased. - Trials 1 and 3 had almost the same settings (60 layers, lr 1.8e-4 vs 1.9e-4) but AUCs of 0.773 and 0.748, so the noise is about the size of the gaps between trials. - This is why the test set is used only once, after all choices are made, and why the reported performance comes from the test set, not from the best validation score.

The grouped means in Figure 2.7f back up the conclusion above: - AUC rises steadily with the number of unfrozen layers: 0.691 (0) → 0.717 (10) → 0.745 (30) → 0.761 (60). - Dropout barely matters: 0.719–0.727. - Learning rate on its own correlates only weakly with AUC (Spearman 0.12) inside the searched range.

So the number of unfrozen layers mattered most.

Bonus: Grad-CAM

scripts/gradcam.py computes Grad-CAM from the last convolutional block of MobileNetV2 (7×7×1280) for 4 correct and 4 wrong test predictions at t = 0.771.

What the model looks at. - Correct AI cases. On the psychedelic collage, the heat sits on the over-detailed face with its saturated, repeated textures. On the weathered-face portrait, it covers the eyes and the unnaturally uniform skin "cracks". These are plausible generator artefacts. - Correct real cases. For the studio headshot, the evidence for AI is weak and centred on the face, so p = 0.05. For the child-style drawing, it sits on a small region at the bottom. - Real images flagged as AI. - On the paint palette (p = 0.92), the model focuses on the dense, colourful paint texture in the corner, not on any photographic flaw. - On the crowd photo (0.91), it focuses on the repeated pattern of tiny faces at the bottom.

Both confirm the hypothesis from 2.6: busy, saturated, repetitive texture is read as "AI". - AI images missed. - On the leopard (0.46), the attention spreads over the fur and the background, and nothing stands out. - On the photorealistic portrait (0.70, just under the 0.771 threshold), the attention is on the face, but the face is clean enough to pass as real.

Conclusion. - The model mostly uses texture and colour statistics in salient regions (faces, dense patterns). It is not keying on watermarks or borders, which is good. - Texture is also its weakness: real artworks and crowded scenes trigger it, and clean photorealistic AI faces escape it.

What went wrong. - My first Grad-CAM version rebuilt the forward pass layer by layer. In Keras 3, preprocess_input is stored as a graph op inside the saved model, not as a layer in model.layers, so the rebuild skipped the [-1, 1] scaling. The heat maps looked plausible, but the probabilities were wrong (0.24 instead of 0.999 for the same image). - I found it by comparing against the inference module's output. I now re-apply preprocess_input and assert that Grad-CAM's p(AI) equals model(x) for every image. This was a small, real example of the training/serving-skew problem discussed in 4.1.

Definitions (my own words): - Experiment: a named folder that groups runs trying to solve the same problem (toy-fashion-mnist, VisionGuard). - Run: one execution of the training code, with a unique id, start time, status and source commit. - Parameter: an input I chose before the run that does not change during it (learning rate, dropout). It is logged once. - Metric: a number measured by the run, possibly many times with a step (val_loss per epoch, final test F1). - Artifact: any output file stored with the run (plots, split lists, pip_freeze.txt, the model). - Tag: free-form key/value metadata about the run (git commit, data hash, seed, "manual" vs "autolog"). It is used to search and filter runs.

3.3 Instrumenting VisionGuard training

src/train.py logs every run to the VisionGuard experiment: - Tags: - git_commit (from git rev-parse HEAD); - dvc_data_md5 (the hash read from data.dvc, which ties the run to the exact data version); - seed=42; - model; - logging. - Parameters: every CLI argument (lr, ft_lr, dropout, epochs, ft_epochs, augmentation), plus img_size and batch. - Per-epoch metrics: loss, accuracy, precision, recall and AUC for training and validation. - Final metrics: best_epoch_stage*, threshold, final_val_* and, with --test, test_*.

Manual approach (--logging manual, run mobilenet_manual, Figures 3.3a–e). - A custom Keras callback EpochLogger calls mlflow.log_metrics(logs, step=offset+epoch) at the end of each epoch. - The step offset makes stage 2 continue on the same x-axis as stage 1. - I decide exactly what is logged and how it is named.

Autolog approach (--logging autolog, run mobilenet_autolog, Figures 3.3f–g). mlflow.tensorflow.autolog() hooks into model.fit and captures, without any code: - every fit argument and optimizer setting (43 parameters, e.g. opt_name=adam, opt_learning_rate, batch_size, class_weight); - per-epoch metrics; - a model summary; - TensorBoard logs; - early-stopping info.

What each approach captures or misses. - Autolog is broad but generic. - Every fit() call starts its step counter at 0, so the stage-2 curves overwrite stage 1 instead of continuing it (its charts show only 2 steps). - It can't know domain values: the validation-chosen threshold, the test metrics, the confusion matrix, or the data hash. - Manual logging is precise but only as complete as my code. It missed the optimizer internals, which autolog logged for free.

I kept both: autolog for the automatic extras, plus manual calls for the domain values.

What went wrong. - The first autolog run failed (red ✗ in Figures 3.3h–i). Autolog tried to log the model with mlflow.keras.log_model, which failed for the nested MobileNetV2 model. - MLflow 3 had also deprecated artifact_path there. - I set log_models=False, wrapped log_model in try/except, and save the .keras file as a plain artifact (model_file/) as a fallback. scripts/finish_autolog_run.py completed the logging for the autolog run.

3.6 Model registry

What I did. - scripts/register_models.py registered L230518_A2_Ops_VisionGuard from the runs' model files, with two versions: - version 1 is mobilenet_manual, alias challenger; - version 2 is mobilenet_ft_lr1e-4, alias champion. - Each version carries the tags run_name and threshold (Figure 3.6a). - scripts/load_champion.py <image> resolves models:/…@champion with MlflowClient.get_model_version_by_alias, downloads that version's .keras, loads it and classifies one image.

How the champion file reaches the server (and why not per request). - scripts/export_champion.py downloads the champion once into models/champion.keras and writes champion_meta.json (version 2, run id). - The web container mounts that folder, and the cloud API image has it built in. - Serving therefore never calls DagsHub. A registry call per request would add seconds of latency, fail whenever DagsHub is down, and hit API rate limits. - Promoting a new model means: move the alias, re-run the export, then restart or rebuild.

This script prints the registry tag threshold 0.366, the validation-F1 threshold stored when the version was registered. The deployed services use the stricter 0.771 chosen in 2.5, set through the THRESHOLD environment variable, so promoting a model never silently changes the false-alarm policy.

Chapter 4: Flask web application

Code layout: - app/ is the web app: the factory, routes, database and templates. - serving/ holds the inference and validation code shared with the API. - api/ is the cloud model API. - wsgi.py is the production entrypoint.

4.1 Inference module

serving/inference.py::Predictor (Figure 4.1): - loads champion.keras once in its constructor; - reads the version from champion_meta.json; - runs one warm-up prediction.

predict(bytes) calls the same function used in training, src/preprocess.py::decode_resize (decode to 3 channels, then bilinear resize to 224×224). Then it runs the model, which contains preprocess_input internally, and returns: - label: "AI-generated" if p ≥ threshold, else "Real"; - p_ai; - confidence: p for AI, 1−p for Real; - threshold, model_name, model_version and latency_ms.

Measured on my laptop: loading the model takes 36.7 s; one prediction takes about 0.3 s.

model v2 loaded once in 36.7s, threshold 0.771
…/AiArtData/…qFcGNfN66Fp4….jpeg   -> {'label': 'AI-generated', 'p_ai': 0.9994, 'confidence': 0.9994, …, 'latency_ms': 337.2}
…/RealArt/…lindsey-pattison….jpg  -> {'label': 'Real', 'p_ai': 0.0462, 'confidence': 0.9538, …, 'latency_ms': 268.5}

Why loading per request is unacceptable. - Every request would take about 37 s instead of 0.3 s, roughly a 100× slowdown. - Every request would re-read 17 MB from disk and re-allocate the whole TF graph. - Concurrent users would multiply the memory use and crash the container.

Loading once at start-up pays the cost one time, and every request after that is fast.

Why training and serving preprocessing must match. - The model only learned the mapping for inputs prepared the training way. - Typical drifts include: - [0, 1] instead of [0, 255] scaling; - a crop instead of a stretch; - RGBA handled differently; - nearest-neighbour instead of bilinear resizing. - Any of these produces inputs the model never saw. The predictions then silently degrade (training/serving skew), and no error is raised. - I avoid this by construction: both paths import the same decode_resize, and the [-1, 1] scaling lives inside the saved model.

Validation (serving/validation.py): 1. Wrong type. Only .jpg, .jpeg and .png are accepted, the formats the model was trained on. Anything else returns 400 "Unsupported file type". 2. Too large. MAX_CONTENT_LENGTH = MAX_UPLOAD_MB (5 MB). Werkzeug rejects larger uploads before reading them, and a custom 413 page explains the limit. 3. Looks like an image but can't be decoded. Pillow fully decodes the bytes (Image.open + load). A .jpg containing junk returns 400 "could not be decoded". The content format must also really be JPEG or PNG, whatever the extension says.

Other protections: - File names are sanitised with werkzeug.secure_filename, so ../../evil name.png is stored as evil_name.png and can't escape a folder. - Nothing is kept on disk. Werkzeug normally spools uploads over 500 KB into a temporary file. app/__init__.py::InMemoryRequest overrides _get_file_stream to use BytesIO, so the image only ever exists in RAM (bounded by the size limit) and is discarded after the request. Only its SHA-256 is stored. - Friendly error pages (error.html) cover 400, 404, 413, 503 (model API down) and 500. The 500 page logs the stack trace but never shows it to the user. - Tests. tests/test_app.py checks all three failure cases, file-name sanitising, the DB trail, /health, the 404 page and the API key (8 tests, all passing).

Chapter 6: Containerisation with Docker and Docker Compose

6.1 Docker warm-up

I practised with the ready-made nginx:alpine image before touching my own project:

What each step shows: - -v made my host folder appear inside the container, so editing index.html on Windows changes the page without a rebuild. - -p 8081:80 forwarded host port 8081 to the container's port 80. - Inside the container whoami returns root. That is the default which my own Dockerfile avoids (6.2).

Definitions (my own words): - Image: a read-only template (filesystem + metadata such as the default command), built from a Dockerfile and identified by name:tag. - Container: a running (or stopped) instance of an image. It is a process with its own isolated filesystem, network and process space, plus a thin writable layer on top of the image. - Layer: each Dockerfile instruction produces a filesystem diff. Layers are stacked, shared between images and cached, so unchanged steps are not rebuilt. - Volume: storage managed outside the container's writable layer. Data in it survives container removal (our Postgres data), or it maps a host folder into the container (our model). - Port mapping (-p host:container): forwards a port on the host to a port inside the container's private network, e.g. -p 5000:5000 makes the app reachable at localhost:5000.

6.2 Dockerfile for the web app

The file is Dockerfile. The order of instructions, and why: 1. FROM python:3.12-slim. It is Debian slim: about 120 MB instead of about 1 GB for the full python:3.12 image. It still uses glibc, so TensorFlow wheels install without compiling (Alpine's musl would force source builds). 2. ENV. No .pyc files, unbuffered logs, PIP_NO_CACHE_DIR, and TF log level 2. 3. Copy only the requirements files, then pip install --no-cache-dir. - This layer is the slowest and biggest (TensorFlow). - Docker reuses a cached layer as long as its inputs are unchanged. Because only the requirements files are copied before it, editing Python code doesn't invalidate this layer. - A code change rebuilds in seconds instead of re-downloading about 600 MB. 4. Copy the source code last (src/config.py, src/preprocess.py, serving/, app/, api/, wsgi.py). 5. useradd app + USER app. The container runs as an unprivileged user (UID 10001). A compromise of the app would not have root inside the container. 6. HEALTHCHECK. It calls /health every 30 s, with a 60 s start period because the model takes time to load. Docker and Compose then report healthy or unhealthy. 7. CMD ["python", "wsgi.py", "web"]. It starts waitress, with debug off.

Ignore file. .dockerignore excludes venv/, data/ (500 MB), mlruns/, tuner_logs/, .git, .env and all non-champion models. This keeps the build context small and keeps secrets out of the image.

Secrets. No secret appears in the Dockerfile. Passwords and keys arrive at run time as environment variables, from Compose, or as encrypted environment variables on the cloud host.

TensorFlow package. I chose tensorflow-cpu==2.21.0 (with keras==3.15.1, the training versions) instead of tensorflow. - The full Linux wheel bundles CUDA/GPU kernels, which the server (no GPU) would never use, and its installed size is several hundred MB bigger. - Inference on one 224×224 image takes about 0.3 s on a CPU, which is fast enough for this product.

6.3 Compose stack

The file is docker-compose.yml. It defines two services: - db: postgres:16-alpine. - Data lives in the named volume pgdata, so history survives docker compose down and rebuilds. - Health check: pg_isready every 5 s. - It has no ports: section, so Postgres is reachable only on Compose's internal network and is closed from outside. - web: built from the Dockerfile. - depends_on: db: condition: service_healthy means it starts only when Postgres accepts connections, so it never crashes on a not-yet-ready DB. - It reaches the DB by service name: DATABASE_URL=postgresql+psycopg://…@db:5432/…. Compose's internal DNS resolves db. - It publishes port 5000 for the browser.

Passwords. All passwords and keys are ${VAR} substitutions read from the untracked .env. .env.example (committed) lists every variable with placeholder values.

How the model reaches the container: mounted. ./models:/models:ro (read-only bind mount). Reasons: - The model is versioned by the registry, not by the image. Promoting a new champion means re-running scripts/export_champion.py and restarting the container, with no rebuild. - The 17 MB model is not baked into an image that CI builds from GitHub, where models/ is git-ignored. - Read-only means the app can't modify it.

For the cloud, the opposite choice is right, and Dockerfile.api builds the model in. That is explained in Chapter 7.

Proof that the database port is closed, and a trap I fell into. - docker compose port db 5432 returns nothing usable ("invalid IP:0"): Compose publishes no host port for db. - docker compose ps lists it only as 5432/tcp, with no 0.0.0.0: mapping. - docker inspect l230518_a2_ops-db-1 confirms it: PortBindings {} and "5432/tcp": null.

However, Test-NetConnection localhost -Port 5432 returned True (Figure 6.2). From the logs and tools alone I traced why: - netstat -ano shows PID 7268 listening on 5432. - tasklist names it postgres.exe, which is the Windows service postgresql-x64-17, a separate PostgreSQL 17 installed natively on my laptop for another course. - The container runs PostgreSQL 16.

So the open port belongs to a different server. The Compose database itself is only reachable on the internal network, as db:5432 from web. The lesson: a port check proves a port is open, not which process owns it.

> netstat -ano | findstr :5432          TCP 0.0.0.0:5432  LISTENING  7268
> tasklist /FI "PID eq 7268"            postgres.exe   (service postgresql-x64-17)
> docker inspect l230518_a2_ops-db-1 --format '{{json .HostConfig.PortBindings}} {{json .NetworkSettings.Ports}}'
{} {"5432/tcp":null}

7.1 Choosing the platform

I tried three platforms before settling on Vercel: - Google Cloud Run needs a billing account even for free-tier use. I created the project l230518-a2-ops (Figure 7.1a), but Google rejected my payment card, a SadaPay virtual card included (OR_BACR2_31, Figure 7.1b). - Azure for Students needs only a university email, but sign-in failed because of a problem with my university account password. - Vercel (the Hobby plan, signed in with GitHub, no card) is named in the assignment. It hosts the model API; Flask and the database stay on localhost, as Task 7 asks.

The obstacle: Vercel can't run TensorFlow. A Python function there is limited to about 250 MB once unzipped, and tensorflow-cpu alone is larger. There is also no persistent disk and a 4.5 MB request-body limit.

The solution: serve a TFLite copy of the champion. - scripts/export_tflite.py exports champion.keras to a SavedModel and converts it with TFLiteConverter to champion.tflite. It stays float32 (no quantisation) to keep accuracy identical, and is 8.9 MB. - The [-1, 1] preprocess_input op is part of the converted graph. - The function runs it with Google's LiteRT runtime (ai-edge-litert, about 60 MB unzipped). The whole function comes to roughly 130 MB. - serving/lite.py::decode_resize_np replaces TF preprocessing with Pillow decoding plus a NumPy port of tf.image.resize's bilinear kernel (half-pixel centres, no antialiasing).

7.2 Checking that the cloud model gives the same answers

Changing the runtime and the preprocessing is a deliberate change to the serving path. That is exactly where training/serving skew (4.1) comes from, so I measured it before deploying. scripts/check_tflite_parity.py compares, on all 146 test images (reports/tflite_parity.csv):

Comparison max abs Δp(AI) mean abs Δp
Keras vs TFLite, same TF preprocessing (conversion only) 3.1 × 10⁻⁶ 5.3 × 10⁻⁷
Keras + TF preprocessing vs TFLite + NumPy preprocessing (what Vercel computes) 3.6 × 10⁻² 4.9 × 10⁻³
Same decision at t = 0.771 146 / 146

The conversion is exact. The remaining gap comes from preprocessing, and I traced it to the JPEG decoder rather than my resize code: - Decoding with TF and resizing with my NumPy code differs from tf.image.resize by at most 0.04 pixel levels, which is rounding. - tf.io.decode_image defaults to libjpeg's fast integer DCT, and Pillow uses the accurate one. Their pixels differ by up to 20/255. - With dct_method="INTEGER_ACCURATE", TF matches Pillow exactly.

Both decoders are valid, and Pillow has no option for TF's fast mode. Because the effect is small (mean Δp 0.005) and never flips a decision on the test set, I accepted it and documented it, instead of shipping TensorFlow just to decode JPEGs.

7.5 Limits and what went wrong

  • Two failed providers. Google billing and Azure sign-in both failed. Because the API is an ordinary Flask app configured only through environment variables, moving between providers changed no application code.
  • Upload limit. Vercel's 4.5 MB body limit forced the API limit down to 4 MB. In remote mode the web app also uses MAX_UPLOAD_MB=4, so users get the friendly 413 page locally instead of an opaque error from Vercel.
  • Routing bug on the first deploy (Figure 7.5). I first used an api/index.py function with a vercel.json rewrite of /(.*) to /api/index. Every call returned Flask's 404, /health included. The Vercel logs showed requestPath: /health, while Flask itself received GET /api/index, because the rewrite replaces the path the WSGI app sees. I switched to Vercel's Flask framework preset (app.py at the root, no rewrites), which forwards the original path.
  • Cold starts. The first request after idle starts a new function instance and loads the model (about 1–3 s).
  • Different runtime. The deployed model is the TFLite conversion, not the .keras file. The parity check in 7.2 is the evidence that it makes the same decisions.

Chapter 8: Integrating Flask and the API

How it works. - The Flask app keeps running on localhost in Docker Compose, with Postgres beside it. - With INFERENCE_MODE=remote, app/predictors.py::RemotePredictor: - keeps one requests.Session with the X-API-Key header set; - POSTs the validated image bytes to MODEL_API_URL/predict, with a 30 s timeout that is enough for a cold start; - stores the returned decision in the database with mode='remote'. - If the API is unreachable or returns an error, the user sees a friendly 503 page and nothing wrong is logged as a decision. - /health also reports whether the cloud API is reachable and which model version it serves.

Why this design. - The same web code runs both ways; only environment variables change. - The heavy model runs in the cloud. - The database and the UI stay local, as the task asks.
